10 — CONFORMITÉ RGPD & PROTECTION DES DONNÉES PERSONNELLES

Dans le cadre de la réalisation de la plateforme Cicados, j'ai intégré dès la phase initiale de cadrage (Sprint 0) les exigences réglementaires européennes du Règlement Général sur la Protection des Données (RGPD - Règlement UE 2016/679) ainsi que les recommandations de la CNIL. La protection de la vie privée des utilisateurs et la souveraineté de leurs données ont constitué un critère d'architecture majeur de mon projet.

10.1 Démarche « Privacy by Design » & Cadre Légal

J'ai adopté une démarche de Protection des données dès la conception (Privacy by Design) et de Protection par défaut (Privacy by Default) :

  • Transparence : L'utilisateur est informé de la finalité exacte de chaque information recueillie lors de son inscription ou de ses réservations de tables.
  • Sécurité Préventive : Aucun accès anonyme non autorisé n'est toléré sur les ressources personnelles des membres (profil, messages, réservations privées).
  • Proportionnalité : Les fonctionnalités de réservation, de consultation de la ludothèque et de participation aux tournois TCG ont été conçues pour fonctionner avec le minimum absolu de données identifiantes.

10.2 Principe de Minimisation des Données (Article 5.1.c RGPD)

Conformément au principe de minimisation, je n'enregistre en base de données MySQL que les attributs strictement indispensables à la fourniture des services du café-boutique :

  • Courriel (email) : Identifiant unique de connexion et vecteur d'acheminement des confirmations.
  • Mot de passe (password) : Haché de manière irréversible via l'algorithme Bcrypt (coût de salage de 10). Aucun mot de passe en clair ne transite durablement ni n'est persisté.
  • Nom & Prénom (firstname, lastname) : Requis pour l'accueil physique au comptoir du café-boutique.
  • Pseudonyme (pseudo) : Pseudonyme public modifiable affiché sur les cartes de tournois et dans les listes de participants, garantissant l'anonymat du nom patronymique vis-à-vis des autres joueurs.
  • Photo de profil (avatar_url) : Téléversement facultatif géré via Multer avec validation stricte du type MIME réel.
🚫 Données superflues délibérément exclues : Aucune collecte de numéro de téléphone obligatoire, aucune géolocalisation ou traceur GPS de l'utilisateur, et aucun stockage de coordonnées bancaires en base de données. Pour la feuille de route V2, la gestion des paiements Stripe s'effectuera par tokenisation déléguée conforme au standard de sécurité bancaire PCI-DSS.

10.4 Mesures Techniques et Organisationnelles de Sécurité (Article 32 RGPD)

Pour garantir la confidentialité et l'intégrité des données personnelles face aux risques d'accès illégitime ou de fuite, j'ai implémenté plusieurs barrières techniques appuyées par le code source :

1. Hachage Cryptographique Unidirectionnel & Authentification JWT

Dans backend/src/controllers/auth.controller.js, je sale et hache les mots de passe avec l'algorithme bcryptjs (coût de salage de 10). À la connexion, je délivre un JSON Web Token (JWT) signé en HMAC-SHA256 valide 24 heures : 

// Extrait réel : backend/src/controllers/auth.controller.js
import bcrypt from 'bcryptjs';
import jwt from 'jsonwebtoken';

// Génère un token JWT sécurisé et temporisé
const generateToken = (user) => {
    return jwt.sign(
        { id: user.id, email: user.email },
        process.env.JWT_SECRET,
        { expiresIn: process.env.JWT_EXPIRES_IN || '24h' }
    );
};

// Hachage fort avant insertion SQL (aucun mot de passe en clair persisté)
const salt = await bcrypt.genSalt(10);
const hashedPassword = await bcrypt.hash(password, salt);

2. Neutralisation des Injections SQL par Requêtes Préparées

Dans backend/src/models/user.model.js, toutes les requêtes sont exécutées via des déclarations préparées avec le marqueur d'emplacement ?. La commande SQL est isolée des valeurs injectées par l'utilisateur : 

// Extrait réel : backend/src/models/user.model.js
async findByEmail(email) {
    const sql = 'SELECT id, email, password, firstname, lastname, pseudo, role, avatar_url FROM users WHERE email = ?';
    const [rows] = await db.query(sql, [email]); // Placeholder '?' étanche
    return rows[0] || null;
}

10.5 Exercice des Droits des Personnes Concernées (Articles 15 à 21 RGPD)

L'architecture de Cicados permet à chaque membre d'exercer ses droits en toute autonomie :

  • Droit d'accès et de rectification (Articles 15 & 16) : Le membre consulte et modifie ses informations personnelles en direct depuis son profil (Profile.jsx connecté à la route PUT /api/auth/profile).
  • Droit à l'effacement / « Droit à l'oubli » (Article 17) : L'utilisateur peut supprimer définitivement son compte depuis son profil, ou l'administrateur peut procéder à l'effacement depuis son tableau de bord.

3. Intégrité SQL en Cascade (ON DELETE CASCADE)

Dans backend/schema.sql, la structure relationnelle garantit qu'aucune donnée orpheline ne subsiste lors de la suppression d'un compte utilisateur : 

-- Extrait réel : backend/schema.sql (Purge automatique Art. 17 RGPD)
CREATE TABLE reservations (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    user_id INT UNSIGNED NOT NULL,
    ...
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
-- Appliqué à l'identique sur tournament_registrations, event_registrations et messages

4. Endpoint Dédié au Droit à l'Oubli (DELETE /api/auth/delete-account)

J'ai implémenté un contrôleur dédié permettant au membre connecté de purger l'ensemble de ses données personnelles : 

// Extrait réel : backend/src/controllers/auth.controller.js
export const deleteAccount = async (req, res) => {
    try {
        const userId = req.user.id;
        await User.delete(userId); // Déclenche le ON DELETE CASCADE dans MySQL
        res.status(200).json({ message: 'Compte et données personnelles purgés avec succès (RGPD).' });
    } catch (error) {
        res.status(500).json({ error: 'Erreur serveur lors de la suppression du compte' });
    }
};

6. Politique « Zéro Traceur Tiers » et Cookies CNIL

La plateforme Cicados applique une politique stricte de « Zéro Traceur Tiers ». Elle n'embarque aucun outil de pistage publicitaire ou de profilage comportemental externe (ni Google Analytics, ni pixel publicitaire). L'unique donnée persistée côté client est le jeton de session JWT dans le localStorage du navigateur. Étant strictement nécessaire à la fourniture du service d'authentification expressément sollicité par l'internaute, ce traceur technique est exempté de recueil préalable de consentement par bandeau intrusif, conformément aux lignes directrices de la CNIL.
