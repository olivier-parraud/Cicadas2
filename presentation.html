La Solution Cicados

⚡ L'Application

02. LA CONCEPTION
Modélisation BDD (MCD)

🗄️ Entités Clés

  • USER : Profils (admin, client), identifiants sécurisés.
  • TABLE : Identifiant, capacité de joueurs, statut.
  • RESERVATION : Horodatage de début, fin et taille du groupe.
  • GAME : Caractéristiques du jeu issues de BGG.

🔗 Relations Métier

  • Une réservation est liée à 1 utilisateur et 1 table.
  • Un utilisateur peut effectuer plusieurs réservations.
  • Gestion des liaisons pour éviter les redondances d'information.
02. LA CONCEPTION
Traduction Relationnelle (MLD / MPD)

⚙️ Structure SQL

  • Clés Primaires : Identifiants uniques par table.
  • Clés Étrangères : Liens physiques entre tables.
  • Types : Optimisation des formats (INT, VARCHAR, DATETIME).

🔒 Contraintes d'Intégrité

  • Clés uniques sur l'email utilisateur.
  • Cascade de suppression lors de la suppression d'un compte.
  • Indexation sur les champs de recherche clés (dates).
03. DEVELOPPEMENT
Fct 1 : Le Besoin (Réservations)

🎯 Objectif Métier

  • Empêcher qu'une même table soit réservée deux fois en même temps.
  • Vérifier que la capacité de la table correspond au groupe de joueurs.
  • Gérer l'amplitude horaire d'ouverture de l'établissement.

🔄 Parcours de Réservation

  • Le client choisit une date, une heure et le nombre de convives.
  • L'application interroge la disponibilité des tables en temps réel.
  • Confirmation instantanée à la validation du formulaire.
03. DEVELOPPEMENT
Fct 1 : L'Algorithme Anti-Conflit

🧮 Comparaison d'intervalles

  • Utilisation de la logique SQL d'intersection d'intervalles.
  • Formule : (Debut_Existant < Fin_Demandee) ET (Fin_Existant > Debut_Demandee).
  • Isolation des tables déjà réservées sur le créneau demandé.

🏗️ Validation Backend

  • Exclusion des tables réservées du jeu de résultats SQL.
  • Sélection de la table disponible ayant la capacité la plus proche.
  • Rejet de la demande si aucune table n'est disponible.
03. DEVELOPPEMENT
Fct 1 : Difficulté & Résolution

⚠️ Difficulté

  • Gestion des conflits d'écriture lors de réservations simultanées.
  • Prise en compte des créneaux partiels à cheval sur plusieurs heures.
  • Variabilité des capacités de tables.

✅ Résolution

  • Mise en œuvre de requêtes SQL avec transaction (`START TRANSACTION`).
  • Lock des lignes SQL pour forcer un traitement séquentiel en cas de concurrence.
  • Validation complète côté API Express avant insertion.
03. DEVELOPPEMENT
Fct 2 : Le Besoin (API BoardGameGeek)

🎯 Objectif Catalogue

  • Afficher des fiches de jeux riches (images, durées, règles).
  • Éviter aux gérants la saisie fastidieuse de centaines de jeux.
  • Assurer des données de référence (âge, nombre de joueurs).

🎲 Choix de BoardGameGeek

  • La plus grande base de données de jeux de société au monde.
  • API gratuite et accessible publiquement.
  • Recherche dynamique par mot-clé à partir du site.
03. DEVELOPPEMENT
Fct 2 : Architecture du Proxy

🏗️ Proxy Node.js

  • Le frontend n'interroge pas l'API externe (évite les blocages CORS).
  • Le backend Express sert de pont sécurisé vers BGG.
  • Filtrage et nettoyage des données reçues.

🔄 Conversion XML vers JSON

  • BGG retourne du XML lourd et complexe.
  • Utilisation de convertisseurs XML2JS côté backend.
  • Envoi d'un format JSON épuré et facile à consommer pour React.
03. DEVELOPPEMENT
Fct 2 : Difficulté & Résolution

⚠️ Difficulté

  • Temps de réponse très variables de l'API BGG.
  • Risque d'indisponibilité bloquant l'affichage du catalogue.
  • Structures XML inconsistantes selon les fiches de jeux.

✅ Résolution

  • Mise en place d'un cache local des requêtes.
  • Système de secours (Fallback JSON) avec données locales pré-remplies.
  • Gestion d'erreurs asynchrones robuste avec retour d'état visuel.
03. DEVELOPPEMENT
Fct 3 : Le Besoin (Authentification)

🎯 Sécurisation Applicative

  • Sécuriser l'accès à l'administration de l'établissement.
  • Permettre aux clients de voir et modifier leurs réservations.
  • Protection des mots de passe et données personnelles (RGPD).

🔑 Rôles Utilisateurs

  • Admin : Contrôle total sur les tables et réservations.
  • Client : Réservation et gestion de profil.
  • Visiteur : Consultation simple du catalogue de jeux.
03. DEVELOPPEMENT
Fct 3 : Authentification JWT & Zod

🎫 Jeton JWT (JSON Web Token)

  • Signature du token côté serveur lors de la connexion.
  • Stockage sécurisé du jeton dans un cookie HTTP-Only.
  • Middleware Express interceptant chaque requête protégée.

🛡️ Validation Zod

  • Validation stricte des formats de données de formulaires.
  • Schémas partagés pour le frontend et le backend.
  • Rejet immédiat des données suspectes ou malformées.
03. DEVELOPPEMENT
Fct 3 : Difficulté & Résolution

⚠️ Difficulté

  • Maintien de l'état de connexion de l'utilisateur sur React.
  • Sécurisation des routes privées sans rechargements infinis.
  • Gestion de l'expiration du jeton de session.

✅ Résolution

  • Création d'un Context d'authentification global sous React.
  • Route `/me` appelée au démarrage pour vérifier la session.
  • Gestion des erreurs HTTP 401 pour déconnexion automatique.
04. POINTS TECHNIQUES
Architecture Découplée SPA

🏗️ Modèle MVC Découplé

  • Client React 19 : Gère l'affichage et l'état.
  • API Express 5 : Centralise la logique métier.
  • MySQL 8 : Assure la persistance des données.

💡 Justification

  • Séparation nette des responsabilités (separation of concerns).
  • Maintenance facilitée et indépendance des technologies.
  • Possibilité d'évolution (création d'app mobile native sur la même API).
04. POINTS TECHNIQUES
Sécurité OWASP

🔒 Protection Données

  • Mots de passe hachés avec le salt fort de Bcrypt.
  • CORS configuré pour bloquer les requêtes non autorisées.
  • Sanitization systématique pour parer les injections de scripts.

🛡️ Parades de Failles

  • Requêtes préparées SQL pour contrer les injections en BDD.
  • Cookies HTTP-Only interdisant l'accès JS au JWT (anti-XSS).
  • Masquage des détails d'erreur système en production.
04. POINTS TECHNIQUES
Performances & Bundling

⚡ Optimisations Frontend

  • Utilisation de Vite à la place de Webpack (démarrage instantané).
  • Lazy Loading des routes React pour alléger le bundle initial.
  • Minification automatique des scripts et des styles lors du build.

⚙️ Optimisations Backend

  • Indexation SQL sur les colonnes de filtre clés.
  • Mise en cache du parsing XML de BoardGameGeek.
  • Optimisation des jointures de tables relationnelles.
04. POINTS TECHNIQUES
Accessibilité (A11y)

♿ Sémantique Web

  • Usage des balises HTML5 appropriées (main, article, section).
  • Présence systématique d'attributs alt sur les images de jeux.
  • Structure de titres (h1, h2, h3) respectant la hiérarchie.

🎨 Lisibilité

  • Contrastes de couleurs vérifiés pour les personnes malvoyantes.
  • Navigation possible et ordonnée à l'aide de la touche Tab.
  • Adaptation des textes pour les outils de synthèse vocale.
04. POINTS TECHNIQUES
i18n & Déploiement

🌍 Internationalisation (i18n)

  • Module i18next configuré pour le support multilingue FR/EN.
  • Détection automatique de la langue système de l'utilisateur.
  • Watch-script de traduction automatique utilisant DeepL.

🚀 Préparation Déploiement

  • Variables d'environnement (.env) pour masquer les secrets.
  • Scripts npm clairs pour configurer et lancer l'application.
  • Code propre, commenté et exempt d'identifiants sensibles.

Difficultés Surmontées

🧗 Obstacles Rencontrés

  • Instabilité des flux de données XML de l'API BGG.
  • Gestion des zones horaires (timezone) lors des réservations.
  • Mise en place d'un état d'authentification robuste.

🔧 Solutions

  • Création d'un parseur XML sur-mesure robuste avec cache.
  • Normalisation des dates au format ISO UTC.
  • Utilisation de Context React et de cookies HTTP-Only.
